Implementation workshop · proposed design

Build a cheap, testable combat-outcome model

Concrete recipe: record complete fights, learn a conditional distribution of their outcomes, sample that distribution inside continuations, and use real combat to verify the resulting card decisions.

This is a proposed baseline, not an implemented repository model. The interactive lab really trains a small categorical predictor in your browser, but on synthetic data. It demonstrates the mathematics and workflow—not expected Slay the Spire performance.

1 · Start with an outcome predictor, not a neural simulator

We already have an expensive function: the frozen combat agent plays a fight. We want to compress its distribution of final outcomes. We do not need to predict every turn or action.

First engineering slice

Begin with supported fights without potions or permanent combat effects. Predict death and final HP. Unsupported states fall back to actual combat.

This proves the pipeline without pretending HP alone represents the full game. Measure how often fallback is needed; a tiny supported subset will not deliver a useful speed-up.

Next slice: preserve joint outcomes

Add potion transitions, then persistent effects. A viable factorization is:

P(death | state)
P(potion outcome | state, survived)
P(final HP | state, survived, potion outcome)

Sample in that order. Conditioning HP on potion outcome preserves their relationship; independent heads sampled independently would not.

A concrete initial architecture

Public combat-start state
  ├─ card tokens: ID, upgrade, relevant mutable attributes
  │    → shared card MLP → sum pool
  ├─ enemy tokens: ID, HP, initial phase/state
  │    → shared enemy MLP → sum pool
  ├─ relic tokens / counters and potion slots as needed
  └─ numeric context: current HP, max HP, relevant resources
          ↓ concatenate
       MLP (e.g. 128 → 128, ReLU)
          ↓
       categorical outcome logits → softmax

For the narrow slice: outcome 0 = death; outcomes 1…max HP = survival at that exact integer HP. Mask impossible outcomes and normalize. Dynamic HP limits need explicit handling; permanent max-HP changes are outside this first slice.

Start with a small pooled model in the style of the existing combat network. The widths above are a proposal, not a tuned requirement. Reusing encoder weights is an experiment; the existing scalar combat value cannot be converted into this outcome distribution.

Why discrete HP? HP is already discrete. An exact categorical target avoids an arbitrary within-bin sampler and preserves lethal thresholds. If labels are sparse, sharing a survivor-HP head or using an ordinal model is a later ablation—not a reason to begin with mean HP regression.

What remains outside the model

Legal card application, rewards, gold, map movement, rest sites, and other known game rules stay in the simulator. Other decisions use fixed controllers. Copy unchanged state rather than asking a network to regenerate it.

Contract: one model approximates one frozen combat checkpoint and search budget. The future strategic horizon belongs to the continuation evaluator, not this local transition model.

Coverage first, repeats selectively

One sampled outcome is a valid training label. You do not need an empirical distribution for every exact deck. The model learns shared structure across states.

Repeat a smaller set of states for auditing calibration and resolving card comparisons. Spend remaining compute on varied, reachable states.

Split before branching

Assign source runs to train, development, and confirmation. Every reward branch, resampled combat, and related snapshot inherits its parent's split.

This prevents almost-identical decks from appearing on both sides and keeps confirmation independent of targeted data collection.

Train with a proper probability loss

p = softmax(model(start_state))
loss = -log(p[observed_outcome])

For logits z, the gradient is:
d(loss)/dz[k] = p[k] - 1[k == observed_outcome]

Each completed fight moves probability toward what actually happened. Across many examples, minimizing expected negative log-likelihood rewards the correct distribution—not just its mean.

Do not casually rebalance death labels. Oversampling deaths changes the implied probability unless corrected by appropriate weights or sampling-aware calibration. Encounter balancing also changes the training mixture; report probability metrics on the intended deployment distribution.
Extension: training the factored potion/HP model
loss = death_binary_cross_entropy
if survived:
    loss += potion_outcome_cross_entropy
    loss += hp_cross_entropy(conditioned on observed potion outcome)

Use observed earlier outcomes while training (teacher forcing); sample predicted earlier outcomes during simulation. Represent legal potion outcomes, including slot changes or generated potions where relevant, rather than assuming only a count is needed. Unsupported mechanics must trigger fallback, not silently disappear.

3 · Lab: actually fit an outcome distribution

This lab generates completed fights, then trains a softmax regression model with gradient descent. Inputs are HP, attack, defense, and optionally attack×defense synergy. Four outcomes stand in for the full HP vocabulary: death, or retaining 25%, 60%, or 90% of starting HP.

The known synthetic generator also uses synergy. Including that feature makes this a deliberately learnable task. Excluding it illustrates a representation limit. This is smaller than the proposed neural model so its behavior is easy to inspect.

A · Data and fit

Changing configuration resets weights and data. Training is deterministic full-batch gradient descent, learning rate 0.25. Test data use separate fixed randomness; labels remain stochastic.

B · Held-out probability quality

NLL: lower is better. The generator's NLL is a reference, not a finite-sample bound. The uniform predictor has NLL log(4) ≈ 1.386.

Suggested experiments:
  1. Train for 300–500 epochs; inspect predicted versus generator probabilities.
  2. Reset with 100 versus 2,400 fights and train to similar convergence. Compare test NLL, not training fit alone.
  3. Exclude synergy, retrain, and inspect high-attack/high-defense states. More training cannot add a missing feature.
  4. Use narrow deck coverage, retrain, and inspect high-attack states. In-distribution validation alone would miss this test.

These controls demonstrate interventions: better coverage, more labels, a more expressive representation, and a proper distributional target. They are not guarantees that every individual synthetic draw improves monotonically.

4 · Reliability is a test suite, not a low loss

Use three levels of validation. Each checks a different promise the model must keep.

Level 1 · Does it predict combat outcomes?

  • Held-out NLL: evaluate the entire distribution. Compare to a simple encounter/starting-HP baseline and the previous model.
  • Death Brier score: average (predicted death probability − actual death indicator)². This keeps catastrophic outcomes visible alongside HP fit.
  • Calibration: group predictions into probability ranges and compare mean predicted death with observed death frequency. Include counts and uncertainty; inspect encounter and HP slices.
  • Threshold calibration: compare predicted and observed probability of surviving with at least H HP for several H values. Mean HP accuracy does not test this.

If probabilities are systematically too sharp, a temperature fitted on a separate calibration split is one possible correction. It cannot fix missing features or bad counterfactual coverage; recheck on untouched data.

Level 2 · Does it choose the right card?

  1. Hold out reward states grouped by source run.
  2. For every choice, estimate success using real continuations with a fixed future selector.
  3. Ask the surrogate evaluator to rank the same choices without seeing those real outcomes.
  4. Measure the real success difference between its recommendation and the inherited selector's choice.
  5. On well-resolved comparisons, estimate regret versus the best-supported alternative. If the real reference cannot resolve a tie, report uncertainty rather than declaring a model error.

Use independent real samples for final recommendation evaluation when candidate selection used noisy reference estimates. Otherwise the apparent best alternative benefits from selection noise.

Level 3 · Does the loop improve real play?

Run complete Act 1 with the new selector at every reward, actual combat, and unchanged other controllers. Pair run seeds and report seed-level uncertainty. This detects compounding errors and newly induced deck distributions.

Record wall time and fallback fraction. A shortcut that routes almost everything back to real combat may be accurate but not useful.

Diagnose failures with a specific intervention

ObservationFirst intervention to test
Training and held-out losses both poorCheck input completeness/label consistency, then a modest capacity ablation on identical data.
Training improves; held-out loss worsensEarly stopping, regularization, or more independent fights—not more epochs.
Historical predictions good; card rankings badAdd counterfactual branches and inspect decision-sensitive state slices.
One-decision recommendations good; complete-act play worseCollect states induced by repeated use; audit continuation-policy mismatch and compounding transition errors.
Predicted improvement disappears under actual combatReject promotion. Refresh data or restrict the surrogate's supported region.
Set numerical acceptance margins after a runtime/variance pilot and before candidate confirmation. There is no universal NLL or calibration threshold that certifies good strategic decisions.

5 · Plug it into card selection without building MCTS first

evaluate_reward(public_state, offered_choices):
    for sampled_future in futures_available_from_public_information:
        for choice in legal_choices(offered_choices):
            state = exact_apply(copy(public_state), choice)
            while not endpoint(state):
                if state is a combat:
                    if surrogate_supports(state):
                        outcome = sample(model(state))
                        state = exact_apply_outcome(state, outcome)
                    else:
                        state = actual_combat(state, frozen_combat_agent)
                else:
                    state = exact_step(state, fixed_controllers)
            record(choice, endpoint_success(state))
    return success_estimates_and_uncertainty()

Future card choices use the inherited selector during this cycle. Match sampled future conditions across candidate choices when valid; preserve correct branch distributions. Sampling only public-information futures prevents hidden-seed lookahead.

What to teach the selector

Store state, legal choices, rollout success estimates, sample counts, and uncertainty. Train a shared state/choice scorer rather than fixed output IDs for “card 1” and “card 2.” Skip is a real action.

A simple initial target is the estimated success rate per action: fit bounded scores to those rates. Use the same continuation-policy version within a training batch/dataset. Keep budgets controlled so adaptively sampled labels do not receive accidental influence.

Alternatively use well-supported pairwise preferences. Do not turn tiny noisy differences into confident one-hot “best card” labels.

Promotion loop

  1. Freeze combat and inherited selector.
  2. Generate comparison labels.
  3. Train a candidate selector.
  4. Validate recommendations using real combat.
  5. Validate repeated use in actual Act 1 runs.
  6. Only then promote it as the next continuation selector.

Keep the real comparison set as a regression test. Add fresh on-policy states without repeatedly tuning on confirmation data.
