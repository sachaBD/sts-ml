Designing card encodings, pooling methods, and action scoring.
The core idea is to treat each zone as a set (multiset) of card feature vectors rather than a list of indices. You then use networks that are permutation-invariant over sets, and let per-card outputs act as pointers for choosing actions.

1. What the structure is
Hand, discard and exhaust are multisets. Their order carries no information, so the network shouldn't have to learn that [Strike, Bash] and [Bash, Strike] are the same.
The draw pile is a multiset with unknown order. Its contents are known; the order is hidden. The exception is cards whose position is known, such as one placed on top by Headbutt, which gets a flag.
Sizes vary. A hand can hold 0–10 cards, and the piles 0–80+.
Actions refer to specific hand cards. So you need one output per card in hand, not a single fixed-size output vector.
Fixed slots indexed by hand position break all four points. The network has to learn "Bash in slot 3" separately from "Bash in slot 1", and the mapping from slot to action is arbitrary.

2. The card encoder
Each card instance maps to a vector: φ(c, s) → ℝ^d.

φ(c,s) = MLP([ E_id[c.id]      # learned embedding, d_id ≈ 16–32
             ; f_static(c)     # cost, type one-hot, base dmg/block/draw/hits,
                               # exhaust/ethereal/retain/innate, target type, upgraded
             ; f_dynamic(c,s)  # cost this turn, playable, effective dmg vs each
                               # enemy, effective block after dex/frail
             ])
What makes the hand easy to learn about:

Engineered features let the network generalise across cards. A 6-damage attack costing 1 looks like other cheap attacks, even for a card that is rarely seen.
The ID embedding keeps unique effects distinguishable. Examples are Feed or Limit Break, whose effects the static features can't express.
Precompute effective values in f_dynamic. Take strength, weak and vulnerable from the simulator and feed in damage after modifiers. Otherwise the MLP has to learn multiplication, which it does badly. This matters directly for your Slime Boss issue, because the question "does this turn push the boss below 50%?" becomes nearly linear in the inputs.
Share one φ across all zones. A separate zone embedding says where the card is:

x_c = φ(c, s) + E_zone[z],   z ∈ {hand, draw, discard, exhaust}
3. Pooling variable-size zones (Deep Sets)
A permutation-invariant summary of a zone uses sum pooling:

p_z = Σ_{c ∈ z} φ(c, s)        # ℝ^d
Use sum, not mean, or add the size explicitly. Mean discards size, and draw-pile size matters because it determines when the reshuffle happens.
Sum plus max is a cheap upgrade that also captures "is there at least one X".
Relation to count vectors: the old counts-over-vocabulary vector n ∈ ℕ^|V| is the special case p_z = nᵀ E_id. Sum pooling generalises it by adding features.
The global state vector:

g = MLP([ p_hand ; p_draw ; p_disc ; p_exh
        ; n_hand, n_draw, n_disc, n_exh
        ; player feats (hp, block, energy, powers)
        ; Σ_e ψ(e)                  # enemies are also a set of 1–5, same trick
        ])
Then V(s) = MLP_v(g) is the value head from the previous answer.

4. Per-card outputs for actions
Contextualise each hand card with the global state, which is an equivariant Deep Sets layer:

h_c = MLP([φ(c,s) ; g])      for c ∈ hand
h_e = MLP([ψ(e,s) ; g])      for each enemy
Score each legal action by the pair (card, target):

ℓ(c, e)  = MLP_π([h_c ; h_e ; g])     # targeted cards
ℓ(c, ∅)  = MLP_π([h_c ; 0 ; g])       # untargeted
ℓ(end)   = MLP_end(g)
π = softmax over legal actions (mask the rest)
This handles any hand size and any number of enemies, and potions fit the same scheme as extra tokens.

Deduplicate identical cards. Two unupgraded Strikes in hand are the same action. Collapse them into one token with a count feature. That shrinks both the search branching and the network input.

5. When to move to attention
Deep Sets only sees the other cards through the pooled g. If card interactions matter (combos, "play X before Y"), replace step 4 with a small transformer:

Tokens: all card tokens x_c, enemy tokens, and one player/CLS token.
No positional encoding. That keeps it permutation-equivariant.
Size: d = 64, 2 layers, 4 heads is plenty.
Outputs: the value comes from CLS, action logits from the hand and enemy tokens as above.
Draw pile tokens: to save cost, feed only the pooled p_draw as a single token instead of every card.
Recommended path
Start with Deep Sets (sections 2–4). It trains fast on CPU and already gives permutation invariance and per-card actions.
Put the effort into f_dynamic: accurate effective-damage and threshold features buy more than extra layers.
Move to attention only if you see errors that depend on sequencing between cards.



It works, and it's the AlphaZero-standard way to do it. Masking then renormalising is exactly the same as a softmax over only the legal logits, and illegal logits get no gradient, so training is unaffected. But as usually implemented it has three weaknesses, and the fixes bring it most of the way back to what I proposed.

1. Free output weights don't generalise

The naive head is ℓ = W g, with W ∈ ℝ^{|A| × d} and one row per action.

Each row is its own parameter, learned only from the positions where that card was playable.
Rare cards get poorly trained logits, and the rich card features you built are ignored on the action side.
Fix: tie the output to the card encoder.
ℓ(a) = q(g)ᵀ φ(card_a, s)        # q: ℝ^d → ℝ^d

Computing this over the whole vocabulary and then masking to the hand gives the same numbers as computing it only for the cards in hand. So with tied weights, "distribution over all cards, then mask" and the pointer approach are the same model. The real choice is between free and tied output weights, and tied wins.

2. Actions keyed on card ID are ambiguous

Two copies of the same card ID in hand aren't always interchangeable:

Snecko Eye and Enlightenment randomise or reduce cost per copy.
Streamline, Claw, Rampage and Ritual Dagger scale per instance.
A retained or upgraded copy differs from a fresh one.

Fix: key actions on the tuple (id, upgraded, cost_now, instance-state bucket), and map each key to one canonical instance. This is the same deduplication rule the search should use anyway.

3. Targets bring back the slot problem

The action space |V| × 5 enemy slots makes the enemy slot index an arbitrary ordering, which is the problem you rejected for the hand. It bites exactly on Slime Boss, where the split puts new enemies into slots. Fix: choose the target autoregressively.

π(c)     = softmax_c( q(g)ᵀ φ(c) )                    # over legal hand keys
π(e | c) = softmax_e( MLP([φ(c); ψ(e); g]) )          # over living enemies
π(c, e)  = π(c) · π(e | c)

This also covers the mid-card choices your fixed action space has to handle anyway: Armaments picking a card to upgrade, Headbutt picking from the discard pile, Discovery choosing one of three. They are all "pick a card from set X", and the same q(context)ᵀ φ(c) head works for each.

Verdict

Keep your framing: one flat distribution over action keys, mask, then sample. Change three things: tie the logits to φ, key actions by instance state rather than ID, and pick the target as a second step. Non-card actions such as end turn and potions can keep free output rows, since there are few of them and they're frequently seen.
