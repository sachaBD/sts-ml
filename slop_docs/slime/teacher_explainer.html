01 · Try futures before committing

What is MCTS?

Monte Carlo Tree Search builds a tree of possible moves. “Monte Carlo” means it uses sampled futures rather than examining every possibility.

  1. Choose a branch: favour promising moves, but also try less-explored ones.
  2. Simulate forward: reach a new position, then estimate its outcome. Playing onward to finish the fight is called a rollout.
  3. Send the score back: update the average score and visit count of the moves on that path.
  4. Repeat, then act: play the most-visited move at the current position—the tree’s root.
Our newer teacher: 20,000 simulations per decision across 8 sampled hidden states—plausible draw orders and RNG, not access to the real future. Its rollouts mostly follow a hand-written heuristic, rather than playing uniformly random moves.

03 · Replace a long guess with a short one

What is a neural value function?

V(state) → one number: expected final combat score

A neural network learns this mapping from examples. During training, it guesses a value, compares it with a supplied label, and adjusts its internal weights to reduce the error.

A value function asks

“How good is this position?”

A policy asks

“Which move should I play?”

We currently train the first, not the second. A value of 0.6 is not necessarily a 60% win chance: our score also rewards surviving HP.

04 · The network’s input

How we encode a state

The state reaches the network in two steps:

  1. Record the visible facts: the encoder converts HP, cards, monsters and other public information into numeric records.
  2. Build a summary: the network combines those records into a fixed-length list of numbers, then uses it to predict the combat value.

Two terms used below:

  • Token: one object’s record—for example, a card’s identity, cost and damage.
  • Vector: a list of numbers, such as [2, 1].

1. Turn each card into a learned summary

Each card record contains two kinds of information:

  • Numbers: cost, damage, block and other measured features. These can go straight into the card network after scaling.
  • Categories: which card it is, which pile it is in, its card type and its target type. Their IDs are labels, not quantities.

An embedding is a learned lookup table. For example, the card ID selects a row of 8 numbers. Training adjusts those numbers so they help predict combat value; we do not assign them meanings such as “aggressive” or “defensive”.

  • Same identity, same lookup: two Strikes use the same card-ID embedding. Different costs, upgrades or zones can still give them different final summaries.
  • Shared network: Strike, Defend and every other card pass through the same transformation—not a separate network per card.
  • Learned output: the 64 numbers describe the card in a form useful for predicting value. They are neither named game stats nor 64 separate predictions.

2. Sum objects into a pool

Sum pooling adds the vectors element by element. Any number of cards becomes one 64-number summary. An empty pile becomes 64 zeros.

Why sum?

Order stops mattering, but multiplicity can still matter. Two identical card vectors contribute twice as much. Mean pooling would make one identical card and two identical cards look the same.

Why separate zones?

A Strike in hand is available now; a Strike in discard is not. Hand, draw, discard and exhaust each get their own pool. We do not flatten the whole deck into one bag.

This model uses sum pooling only—not mean pooling, max pooling or attention. Summing is compact and order-independent, but it can lose distinctions between collections; it is not a reversible encoding.

3. Keep card–target relationships

Separate card and monster pools make it harder to see which attack suits which enemy. So we also build pair vectors: a card’s 64 numbers + a monster’s 64 numbers + 6 damage/target features. Another small network turns those 134 numbers into 64, then we sum the pairs.

Which public facts go into the records?

The current v3 fields are:

PartWhat it contains
Global state50 numeric features: HP, block, energy, turn, powers, incoming damage… Plus IDs for the current decision/selection type.
CardsCard identity, zone, type and targeting; 14 numbers such as upgrade, cost, damage, block and playability.

For example, 60 HP becomes 0.60 in the HP/100 feature. “Strike against this slime” includes damage after relevant modifiers, so the model needn’t relearn all the combat arithmetic.

No peeking: draw-pile contents are visible, unknown draw order and hidden RNG are not. Reordering otherwise identical card records must not change the prediction.
05 · A move is not a card name

How we encode an action

“Play Strike on slime A” and “play Strike on slime B” are different actions.

State interaction record

“How much would this attack damage that monster?” Contains numeric attack/target features. It contributes to the state’s pair pool.

Action record

“Play this card on that monster.” Describes an executable choice. It is not pooled into the current value network.

The C++ action token also supports potions, card selections and end turn. The execution index is a temporary routing address—not a learned meaning for “action 3”.

Important: the current value network does not consume action tokens. Teacher rows store action indices, descriptions, visits and mean scores separately. Search executes an action, then the network evaluates the resulting state.

06 · Our particular value function

Small networks, summed summaries, one score

Our model is called Deep Sets. It handles different numbers of cards and monsters without assigning importance to their list order.

  1. Turn each card and monster into a learned numeric summary using small neural networks.
  2. Summarize card–monster interactions too.
  3. Sum cards separately for hand, draw, discard and exhaust; sum monsters and interactions.
  4. Combine those summaries with global features. A final network outputs one value.

The default hidden width is 64. The final tanh limits the output to −1…1; the training labels determine what that number means.

One current limitation

v3 defines an “offered” card zone for selection choices, but this model only pools the four normal zones. That is a coverage gap, not a feature already handled by the network.

07 · Training labels

Where does each training label come from?

A row is a position before a real move. It is not one row per search simulation, and its value label is not the name of the move to imitate.

First, collect two possible answers

  1. Before the move: save the encoded state and the teacher’s estimate, root_value.
  2. Play the move: usually the teacher’s choice. The current generator can override at most one decision per fight with a random legal move.
  3. After the fight: compute terminal_value and attach that same result to every saved row from the fight.

Search estimate: v̂

“What did search think here?”

Average the root actions’ mean scores, weighted by their visits.

v̂ = Σ(visits × mean score) / Σvisits

Actual outcome: z

“What happened in this fight?”

Loss: 0. Win:

z = (35 + final HP + 4 × potions left) / (55 + max HP)

v̂ is not the best move’s score. It includes exploration of weaker moves. It also depends on the rollout heuristic and sampled hidden states.

z is not a verdict on every move. A good opening can still lead to a loss. Repeated examples let the network learn an average rather than treat one unlucky fight as certainty.

A worked example

Suppose a fight ends in a win at 40/80 HP with no potions. Every row gets z = 75/135 ≈ 0.556. But one row’s search estimate might be v̂ = 0.400, while another’s is 0.520.

Which number should the first row teach?

A possible blend is y = λ × z + (1 − λ) × v̂.


Label y = 0.50 × 0.556 + 0.50 × 0.400 ≈ 0.478

Illustrative numbers, not a recorded row. λ = 0 copies search; λ = 1 learns only from outcomes. A 50/50 blend is an experiment, not an established best choice.

What does the code actually train on today?

  • Existing trainer: uses the older mcts_value label—an MCTS root estimate. It minimizes mean squared error: average((prediction − label)²).
  • New teacher records: store root_value and terminal_value. The trainer has not yet been adapted to select or blend them.
  • Different score scales: older MCTS uses loss = −1, win = 0.5 + 0.5 × HP/max HP. Do not mix those targets with the new score without conversion.

Even the new v̂ and z are not identical objectives: the teacher’s default search adds a small turn penalty on wins and shaping on losses. Align them before treating a blend as one clean target. Keep entire decks together when splitting training and validation data.

08 · The network helps search; it does not replace it

How the final agent uses the value network

Without the network

Search reaches a new position → play a rollout → send its final score back through the tree.

With the network

Search reaches a new position → encode it → predict V(state) → send that estimate back through the tree.
  1. Start search from the actual current position.
  2. Explore simulated moves; use the network at new, unfinished positions called leaves.
  3. If a simulated fight is already over, use its exact score—not a neural guess.
  4. After the search budget is spent, execute the most-visited root move.
  5. Observe the real result and search again for the next decision.
The division of labour: the simulator knows the rules, the network estimates long-term quality, and MCTS decides which move to play.

Implemented: older MCTS calls the Python value model for leaves. Next: train on the new teacher format, then use the teacher’s batch request/submit hooks to evaluate leaves together.

That may improve play or reduce rollout work. Neither speed nor strength is automatic: test on held-out decks at equal wall-clock time as well as equal simulation count.
